# কেন Authentication দরকার?

মঙ্গলবার সকাল। Arif প্রথম চায়ের কাপে চুমুক দেওয়ার আগেই ফোন বাজল। ওপাশে Rafi।

"ভাই, একটা অদ্ভুত ব্যাপার। আমার সবচেয়ে বিক্রি হওয়া পাঞ্জাবিটার দাম সাইটে দেখাচ্ছে 120। কাল রাত পর্যন্ত ছিল 1200। রাতে ওই দামে ছয়টা অর্ডার চলে এসেছে।"

"আপনি বদলেছেন?"

"আমি না। কর্মচারীরাও বলছে করেনি।"

Arif চুপ করে গেল। তার মাথায় একটাই প্রশ্ন ঘুরছে, আর সেই প্রশ্নের উত্তর তার system-এর কাছে নেই: **কে করল?**

---

## ১. প্রথম সংস্করণ: "ভেতরের পেজ তো ভেতরের লোকেরাই দেখবে"

KenaKata তখনো খুব ছোট। একটা server-rendered web application, একটা দোকান (Rafi-র কাপড়ের ব্যবসা), আর তিনটা কাজ: পণ্য দেখানো, customer-এর তথ্য রাখা, অর্ডার নেওয়া।

Nira আগের দিন বলেছিল, "Rafi কাল থেকে সত্যিকারের অর্ডার নেবে। আমাদের হাতে আজকের দিনটাই আছে।"

Arif ঠিক করেছিল, দোকানের সামনের দিক সবার জন্য খোলা থাকবে। Shopper-দের পণ্য দেখতে বা অর্ডার দিতে account লাগবে না। আর ভেতরের দিক, মানে অর্ডারের তালিকা আর দাম বদলানোর পেজ, `/manage` দিয়ে শুরু হবে। ওগুলো তো Rafi আর তার কর্মচারীরাই ব্যবহার করবে। Login পরে বানালেও চলবে।

| Path | কী করে | কার জন্য (Arif-এর ধারণায়) |
|---|---|---|
| `GET /products` | পণ্যের তালিকা দেখায় | সবাই |
| `POST /orders` | নতুন অর্ডার নেয় | সবাই (shopper) |
| `GET /manage/orders` | সব অর্ডার, সঙ্গে নাম-ফোন-ঠিকানা | শুধু Rafi আর তার লোক |
| `POST /manage/products/{id}/price` | পণ্যের দাম বদলায় | শুধু Rafi আর তার লোক |

কোডটা ছিল এরকম:

```go
package main

import (
	"log"
	"net/http"
)

func main() {
	mux := http.NewServeMux()

	// দোকানের সামনের দিক — সবার জন্য খোলা, এটাই চাই
	mux.HandleFunc("GET /products", listProducts)
	mux.HandleFunc("POST /orders", placeOrder)

	// ভেতরের দিক — "শুধু Rafi-র লোক ব্যবহার করবে" (এটা Arif-এর আশা)
	mux.HandleFunc("GET /manage/orders", listAllOrders)
	mux.HandleFunc("POST /manage/products/{id}/price", updatePrice)

	log.Fatal(http.ListenAndServe(":8080", mux))
}

// (Go 1.22+ লাগবে: method সহ route pattern এবং r.PathValue এর জন্য)
func updatePrice(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	price := r.FormValue("price")

	// ... database-এ দাম বদলে দেওয়া হলো ...

	log.Printf("price updated: product=%s price=%s", id, price)
	w.WriteHeader(http.StatusNoContent)
}
```

এবার কোডটা আবার পড়ুন, এবং একটা প্রশ্ন নিয়ে পড়ুন: **কোথায় বলা আছে যে `updatePrice` শুধু Rafi-র লোকেরা চালাতে পারবে?**

কোথাও নেই। "শুধু ওরাই ব্যবহার করবে" একটা আশা। system-এর কোনো নিয়ম নয়। Path-এর নামে `manage` লেখা থাকলে সেটা private হয়ে যায় না। ওটা শুধু একটা নাম।

## ২. ঘটনার পর: log কী বলল

Rafi-র ফোন রাখার পর Arif server-এর log খুলল। যা পেল:

```
2026-10-05T02:14:09Z price updated: product=17 price=120   ip=203.0.113.58
```

(IP-টা এখানে নমুনা হিসেবে বসানো।)

একটা সময়, একটা IP address, আর একটা দাম। এই তিনটা থেকে কয়েকটা প্রশ্নের উত্তর বের করা দরকার:

1. **কে** করেছে? IP address মানুষ নয়। অনেক মোবাইল ইন্টারনেট সংযোগে বহু মানুষ একই public IP ভাগ করে। একটা Wi-Fi-তে পুরো দোকান থাকে। VPN থাকলে তো কথাই নেই।
2. **কীভাবে** ঢুকল? Endpoint-এ তো কোনো পাহারাই নেই। যে কেউ, যেকোনো জায়গা থেকে অনুরোধ পাঠালেই কাজ হয়ে যায়।
3. **ইচ্ছা করে** করেছে, নাকি ভুল করে? সম্ভাবনা অন্তত তিনটা: কর্মচারীর হাত ফসকে যাওয়া, system-এর bug, বা বাইরের কেউ।

লক্ষ্য করুন, তিনটা সম্ভাবনার একটাকেও Arif অন্যগুলো থেকে আলাদা করতে পারছে না। এটা শুধু "বাইরের শত্রুকে ঠেকানো"র সমস্যা নয়। এটা আরও গভীর সমস্যা: **system জানে না কে কী করছে।**

## ৩. Naive solution: URL লুকিয়ে ফেলি

Arif-এর প্রথম সমাধানটা ছিল সবচেয়ে স্বাভাবিক। `/manage` পথটা পাল্টে `/m-x7k2q9` করে দিল। এখন কেউ আন্দাজ করতে পারবে না।

Rafi খুশি। "ঠিক আছে, এখন তো কেউ জানে না।"

কয়েকটা দিন সত্যিই শান্তি। তারপর?

```
গোপন URL:  /m-x7k2q9/orders
      │
      ├─► কর্মচারী লিঙ্কটা WhatsApp/Messenger-এ আরেকজনকে পাঠাল
      ├─► Browser history আর autocomplete (দোকানের shared কম্পিউটারে)
      ├─► Server বা proxy-র access log-এ পুরো path লেখা থাকে
      ├─► একজন কর্মচারী চলে গেল, কিন্তু URL তার মনে আছে
      └─► Bot-রা wordlist ধরে অসংখ্য path অনুমান করে দেখে
```

এটা আসলে দরজায় তালা না লাগিয়ে একটা চিরকুট ঝুলিয়ে রাখা: *"দয়া করে ঢুকবেন না।"*

এখানে দুটো আলাদা ব্যর্থতা আছে, আর দুটোকেই আলাদা করে বোঝা দরকার।

**ব্যর্থতা ১: গোপনীয়তা ফাঁস হয়, আর ফাঁস হলে ফেরানোর উপায় থাকে না।** URL একবার ছড়ালে সবাই সমান। কার কাছে আছে জানা যায় না। বন্ধ করতে হলে URL বদলাতে হয়, আর সবাইকে নতুনটা জানাতে হয়, যার মানে আবার ছড়ানোর ঝুঁকি।

**ব্যর্থতা ২: যদি কখনো ফাঁস নাও হয়, তবুও সমস্যা থেকে যায়।** গোপন URL শুধু বলে "এই string-টা জানে"। বলে না "তুমি কে"। দশজন কর্মচারী একই URL ব্যবহার করলে দাম কে বদলাল, সেটা কখনোই জানা যাবে না। অর্থাৎ ঘটনার মূল প্রশ্ন "কে করল?" এই সমাধানে একটুও এগোয়নি।

> **একটু পেছনে তাকাই।** ক্রিপ্টোগ্রাফিতে উনিশ শতকের শেষ দিকে Auguste Kerckhoffs একটা নীতি দিয়েছিলেন। সহজ করে বললে: একটা system-এর নিরাপত্তা নির্ভর করবে শুধু চাবির গোপনীয়তার ওপর। নকশা বা পদ্ধতি সবাই জেনে গেলেও system টিকে থাকা উচিত। আমাদের গোপন URL-এ চাবি আর নকশা একই জিনিস। পথটা জানাই একমাত্র সুরক্ষা। এটা ভঙ্গুর হওয়ার একটা কারণ।

## ৪. কাদের থেকে, কী বাঁচাতে চাই? (Threat model)

"নিরাপত্তা চাই" একটা ঝাপসা কথা। Threat model হলো সেই ঝাপসা কথাটাকে স্পষ্ট প্রশ্নে বদলানো: **কারা কী করতে পারে, আর কোনটা আমরা ঠেকাতে চাই?**

| কে | কী করতে পারে | উদাহরণ |
|---|---|---|
| বেনামি দর্শক | খোলা endpoint-এ অনুরোধ পাঠাতে পারে | `curl` দিয়ে দাম বদলানো |
| স্বয়ংক্রিয় scanner/bot | খোলা দরজা খুঁজে বেড়ায়, কারও নাম দেখে বাছাই করে না | সাধারণ path-এর তালিকা ধরে চেষ্টা |
| প্রাক্তন কর্মচারী | পুরোনো জানা URL ব্যবহার করে | চলে যাওয়ার পরেও ঢুকতে পারা |
| অসাবধান ভেতরের মানুষ | ভুল করে ভুল জিনিস বদলে ফেলে | ভুল পণ্যের দাম বদলানো |

আর আমরা যে নিরাপত্তা-গুণগুলো (security properties) চাই:

- **Confidentiality:** Customer-এর নাম, ফোন নম্বর, ঠিকানা শুধু যাদের দেখার কথা তারাই দেখবে।
- **Integrity:** দাম, অর্ডার, ঠিকানা শুধু বৈধ উপায়ে বদলাবে।
- **Accountability:** কোনো পরিবর্তন হলে বলা যাবে কে করেছে।

লক্ষ্য করুন, তৃতীয়টা শুধু শত্রুর বিরুদ্ধে নয়। দোকানের সবাই সৎ হলেও accountability ছাড়া "কে ভুল করল?" প্রশ্নটার উত্তর পাওয়া যায় না।

> **মনস্তত্ত্বের একটা ফাঁদ।** ছোট ব্যবসার মালিকরা প্রায়ই ভাবেন, "আমরা তো ছোট, আমাদের কে টার্গেট করবে?" এটা optimism bias-এর একটা চেহারা। সমস্যা হলো, অনেক আক্রমণ কাউকে "টার্গেট" করে না। তারা ইন্টারনেটে খোলা দরজা খুঁজে বেড়ায়, যেখানে পায় সেখানেই ঢোকে। লক্ষ্য হওয়ার জন্য "বড়" হওয়া জরুরি নয়, শুধু খোলা থাকাটাই যথেষ্ট হতে পারে।

## ৫. Better solution: প্রশ্নটা বদলাই

Arif প্রথমে প্রশ্ন করেছিল: "পেজটা কীভাবে লুকাব?" এই প্রশ্নটাই ভুল ছিল। সঠিক প্রশ্ন হলো: **"অনুরোধটা কে পাঠাচ্ছে, আর সেটা আমি কীভাবে জানব?"**

এখানে তিনটা আলাদা ধারণা আছে, যেগুলো প্রায়ই গুলিয়ে যায়:

| ধাপ | প্রশ্ন | উদাহরণ |
|---|---|---|
| **Identification** | তুমি কে বলে দাবি করছ? | "আমি Rafi" |
| **Authentication** | দাবিটা কি সত্যি? প্রমাণ দাও | এমন কিছু, যা আসল Rafi-ই দিতে পারে |
| **Authorization** | তুমি কী করতে পারবে? | (Chapter 2-এর বিষয়) |

দাবি করা সহজ। ইন্টারনেটে একটা বিখ্যাত কার্টুন আছে, যেখানে একটা কুকুর কম্পিউটারে বসে বলছে, "ইন্টারনেটে কেউ জানে না যে তুমি একটা কুকুর।" Authentication ঠিক এই সমস্যার উত্তর। পরিচয় আসলে একটা দাবি। আর সেই দাবির ওপর ভর করে system একটা সিদ্ধান্ত নেয়, মানে বিশ্বাস করে।

প্রমাণ সাধারণত তিন ধরনের হয়:

- **জানা জিনিস** (something you know): password, PIN
- **থাকা জিনিস** (something you have): ফোন, security key
- **তুমি নিজে** (something you are): আঙুলের ছাপ, মুখ

প্রতিটা ধরনের নিজস্ব দুর্বলতা আছে। কোনোটাই নিখুঁত নয়। এই series-এ আমরা ধীরে ধীরে এদের সঙ্গে পরিচিত হব। Password আসবে Chapter 3-এ, একাধিক ধরনের মিশ্রণ (MFA) Chapter 22-এ।

তাহলে সংজ্ঞাটা দাঁড়াল এরকম:

> **Authentication** হলো একটা অনুরোধের পেছনের পক্ষ সম্পর্কে এই যুক্তিসঙ্গত আস্থা (justified confidence) তৈরি করা যে সে-ই, যে সে দাবি করছে।

"আস্থা" শব্দটা ইচ্ছা করে বেছেছি। Authentication নিশ্চয়তা দেয় না। প্রমাণ চুরি হতে পারে, নকল হতে পারে। তাই প্রতিটা প্রমাণ-পদ্ধতির সীমা জানা ততটাই জরুরি, যতটা পদ্ধতিটা জানা।

### কোথায় থাকে এই পাহারা?

একটা সূক্ষ্ম কিন্তু গুরুত্বপূর্ণ কথা। Arif-এর এক সহকর্মী বলতে পারত, "আমরা browser-এ ওই button-টা লুকিয়ে ফেলি, কিংবা JavaScript দিয়ে check করি।" এতে কাজ হবে না। আক্রমণকারী browser ব্যবহারই করে না:

```bash
curl -X POST https://kenakata.example/manage/products/17/price -d "price=120"
```

Browser আমাদের নিয়ন্ত্রণে নেই। যা কিছু client-এ ঘটে, তা আক্রমণকারী এড়িয়ে যেতে পারে। তাই Authentication-এর পাহারা বসাতে হয় **server-এ**, প্রতিটা সুরক্ষিত অনুরোধের ঠিক সামনে।

Arif-এর নতুন কাঠামোটা এরকম হতে পারে। মনে রাখবেন, এখনো আমরা জানি না প্রমাণটা আসলে কী হবে:

```go
package main

import (
	"context"
	"net/http"
)

type identityKey struct{}

// Identity — authentication-এর ফলাফল: "এই অনুরোধ কার পক্ষ থেকে এসেছে"
type Identity struct {
	UserID string
}

// requireAuthentication — ভেতরের route-গুলোর সামনে বসানো পাহারাদার
func requireAuthentication(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id, ok := authenticate(r)
		if !ok {
			http.Error(w, "authentication required", http.StatusUnauthorized)
			return
		}
		ctx := context.WithValue(r.Context(), identityKey{}, id)
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

// authenticate-এর ভেতরে কী হবে, সেটা এখনো ঠিক হয়নি।
// ঠিক সেটাই এই season-এর পরের chapter-গুলোর কাজ।
func authenticate(r *http.Request) (Identity, bool) {
	return Identity{}, false // আপাতত কাউকেই বিশ্বাস করি না
}
```

আর route-গুলো জুড়তে হয় এভাবে:

```go
mux.Handle("GET /manage/orders",
	requireAuthentication(http.HandlerFunc(listAllOrders)))
mux.Handle("POST /manage/products/{id}/price",
	requireAuthentication(http.HandlerFunc(updatePrice)))
```

দুটো জিনিস লক্ষ্য করার মতো।

**প্রথমত,** `authenticate` আপাতত সবাইকে ফিরিয়ে দেয়। শুরুটা খোলা দরজা থেকে বন্ধ দরজায়। "ডিফল্টভাবে অস্বীকার করো, প্রমাণ পেলে অনুমতি দাও।" নিরাপদ নকশা সাধারণত এই দিক থেকেই শুরু হয়।

**দ্বিতীয়ত,** `Identity` এখন প্রতিটা অনুরোধের সঙ্গে চলতে পারে। যে log আগে ছিল:

```
price updated: product=17 price=120 ip=203.0.113.58
```

তা এখন হতে পারে:

```
price updated: product=17 price=120 by=user-4 ip=203.0.113.58
```

এইবার "কে করল?" প্রশ্নের একটা উত্তর পাওয়া সম্ভব। তবে একটা শর্ত আছে। এই উত্তর ততটাই নির্ভরযোগ্য, যতটা নির্ভরযোগ্য আমাদের authentication। যদি দোকানের সবাই একটাই login ভাগ করে ব্যবহার করে, accountability আবার ধসে পড়ে।

> **নামকরণের একটা ফাঁদ।** HTTP-তে `401` status-এর নাম "Unauthorized", কিন্তু আসলে এর মানে "তোমার authentication নেই বা বৈধ নয়"। Authorization-এর ব্যর্থতার জন্য আলাদা `403`, যেটা আমরা Chapter 2-তে দেখব। কোডটা এখানে সরল করা হয়েছে। HTTP specification অনুযায়ী `401` response-এ `WWW-Authenticate` header থাকার কথা। আর server-rendered web app সাধারণত সরাসরি login পেজে redirect করে। ওসব পরে।

## ৬. Trade-off: নিরাপত্তার দাম

পরদিন Nira এল একটা আপত্তি নিয়ে।

"Rafi জিজ্ঞেস করছে, প্রতিবার ঢোকার সময় এসব কেন করতে হবে? সকালে দোকান খোলার সময় ওর হাতে সময় থাকে না।"

Arif উত্তর দিতে গিয়ে বুঝল, সে নিজেও কিছু নতুন সমস্যা ডেকে এনেছে:

- **ঘর্ষণ (friction):** যে কাজ আগে এক ক্লিকে হতো, এখন তার আগে একটা ধাপ।
- **Secret সংরক্ষণের দায়িত্ব:** প্রমাণ বলে যা-ই ঠিক করি, সেটা এখন আমাদের কোথাও রাখতে হবে। চুরি হলে সেটা আমাদের সমস্যা।
- **ভুলে গেলে কী হবে?** Recovery একটা নতুন দরজা। সেই দরজাও আক্রমণের লক্ষ্য হতে পারে।
- **Login নিজেই এখন লক্ষ্য:** আক্রমণকারীরা এবার ঠিক এই জায়গাটায় চেষ্টা করবে।
- **Availability:** সবচেয়ে ব্যস্ত দিনে কর্মচারী ঢুকতে না পারলে ব্যবসা থেমে যায়।

আগে সমস্যা ছিল "দরজা খোলা"। এখন সমস্যা "দরজা আছে, আর সেটা ঠিকমতো বানাতে হবে।" Authentication সমস্যা মেটায়, কিন্তু নতুন কিছু সমস্যা তৈরিও করে। সেগুলো মোকাবিলা করাই এই season-এর বাকি অংশ।

## ৭. Authentication কী সমাধান করে না

এটা মনে রাখা দরকার, নইলে "authentication আছে, তাই আমরা নিরাপদ" ধরনের ভুল ধারণা তৈরি হয়।

- **কে কী করতে পারবে**, সেটা ঠিক করে না। প্রমাণিত ব্যবহারকারী সবকিছু করতে পারবে, এমন নয়। এটা Authorization, Chapter 2-এর বিষয়।
- **প্রমাণটা (যেমন password) কীভাবে নিরাপদে রাখা হবে**, সেটা ঠিক করে না। Chapter 3।
- **একবার প্রমাণ দেওয়ার পর পরের অনুরোধগুলোতে কীভাবে মনে রাখা হবে**, সেটাও এখানে ঠিক হয়নি। HTTP প্রতিটা অনুরোধকে আলাদা ভাবে। Chapter 4।
- **নেটওয়ার্কে আড়ি পাতা** ঠেকায় না। সেটা আলাদা সুরক্ষার (যেমন HTTPS) কাজ। Authentication তার বিকল্প নয়।
- **বৈধ ব্যবহারকারীর ভুল** ঠেকায় না, আর যদি কারও account দখল হয়ে যায়, তখন system তাকে আসল ব্যবহারকারী বলেই মনে করবে।

| কী সমাধান করে? | বেনামি প্রবেশ, "কে করল?" প্রশ্নের শূন্যতা |

## আমরা কী শিখলাম? (What did we learn?)

- Path-এর নামে `manage` লেখা থাকলে সেটা সুরক্ষিত হয় না। "শুধু ভেতরের লোক ব্যবহার করবে" একটা আশা, system-এর নিয়ম নয়।
- গোপন URL ব্যর্থ হয় দুই কারণে: গোপনীয়তা ফাঁস হয় এবং ফাঁস হলে ফেরানোর উপায় নেই, আর ফাঁস না হলেও এটা বলে না ব্যবহারকারী কে।
- সমস্যা শুধু বাইরের শত্রুর নয়। Accountability ছাড়া সৎ ভুলও রহস্য হয়ে যায়।
- Identification হলো দাবি, Authentication হলো দাবির যাচাই, Authorization হলো অনুমতি। তিনটা আলাদা প্রশ্ন।
- Authentication দেয় যুক্তিসঙ্গত আস্থা, নিশ্চয়তা নয়।
- পাহারাটা বসাতে হয় server-এ, client-এ নয়।
- Authentication নতুন দায়ও আনে: secret সংরক্ষণ, recovery, ঘর্ষণ, আর login নিজেই লক্ষ্য হয়ে ওঠা।
